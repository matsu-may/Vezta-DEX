# Polygon LP API feasibility — read-only gate

**Status:** The owner's corrected LP API probe returned `status:200`, one matching pool, valid state shape and positive active liquidity. The independent Polygon RPC probe returned `verified:true` with every pinned-block check true. Unsigned `/lp/create` and `/lp/check_approval` both return HTTP 200 with matching outer shapes. The decoded `mint` desired amounts differ from the API's token amount fields, and both returned approvals are unlimited. These action payloads remain rejected; no LP wallet write is qualified.

The candidate is the native-USDC/WETH Uniswap v3 0.05% pool `0xA4D8c89f0c20efbe54cBa9e7e7a7E509056228D9`, identified in the earlier [pool research](2026-09-27-polygon-weth-usdc.md). Uniswap's [Polygon v3 deployment list](https://developers.uniswap.org/docs/protocols/v3/deployments/v3-polygon-deployments) identifies the `NonfungiblePositionManager` as `0xC36442b4a4522E871399CD717aBDD847Ab11FE88`. A swap route using this pool does not prove the LP API works for this pool.

The current [Uniswap LP integration guide](https://developers.uniswap.org/docs/liquidity/liquidity-provisioning-api/integration-guide) describes `/lp/check_approval`, `/lp/create`, `/lp/increase`, `/lp/decrease`, `/lp/claim_fees` and `/lp/pool_info`. It says approval and transaction validation remain the integrator's responsibility, with the user's wallet signing and broadcasting. Its v3 decrease flow may include fee collection; UI must avoid counting those fees twice. The [pool-info API](https://developers.uniswap.org/docs/api-reference/pool_info) accepts a v3 token pair, fee and chain ID and returns pool identity, tick and liquidity fields. The separate [v3 position-fetching guide](https://developers.uniswap.org/docs/sdks/v3/guides/managing-liquidity/position-fetching) documents owner NFT IDs and `positions(tokenId)` reads; it is not itself an indexed portfolio service.

`node scripts/smoke-lp-pool-info.mjs` makes exactly one authenticated, **read-only** request for Polygon 137, native USDC/WETH and fee 500. It validates the returned pool address, token addresses/decimals, protocol and live-state field shapes. It reads `UNISWAP_LP_API_KEY` if set, otherwise `UNISWAP_API_KEY`, from ignored `apps/api/.env`. The agent's restricted network returned `{"errorKind":"NETWORK"}`, but the owner's host returned `{"status":200,"poolCount":1,"poolMatches":false,"stateShapeValid":false,"activeLiquidityPositive":false}` twice. HTTP 200 establishes endpoint/key access for this read; the false flags **do not** establish which field differs or whether the candidate pool is wrong. The `stateShapeValid` and liquidity flags remain false whenever identity fails, so they are not separate evidence of empty liquidity.

The bounded `poolChecks` output identified: Polygon chain, v3 protocol, expected pool address, native-USDC/WETH pair, fee and state field shapes matched; `tokenDecimalsMatch` was false with `tokenDecimalsTypes:["string","string"]`. The corrected probe checks exact expected decimal values as numbers or canonical strings, preserving rejection of wrong values, reversed token-decimal mappings and noncanonical strings such as `"06"`. It prints `poolChecks` **only on mismatch** and never prints the API key, wallet, request ID, arbitrary upstream strings, raw response or transaction data. The owner's next read-only run passed all three Booleans. Uniswap's [pool-info API reference](https://developers.uniswap.org/docs/api-reference/pool_info) documents the requested token pair, fee, chain and response fields used by this probe.

`node scripts/smoke-lp-onchain.mjs` independently pins one recent Polygon block, reads the canonical v3 factory's `getPool` and fee tick spacing, the pool's factory/token/fee/tick/active liquidity/`slot0` values and both token decimals, then re-reads the block hash. The owner ran it against block `94721672` observed at `2026-09-30T17:00:48.000Z`: `blockFresh`, `blockStable`, `factoryPoolMatches`, `poolFactoryMatches`, `tokensMatch`, `decimalsMatch`, `feeMatches`, `tickSpacingMatches`, `initialized` and `activeLiquidityPositive` were all `true`; overall `verified:true`. This qualifies the fixed v3 0.05% pool for read-only discovery, not unsigned LP actions, fee estimates or wallet writes. The checks follow Uniswap's [v3 pool immutables](https://github.com/Uniswap/v3-core/blob/main/contracts/interfaces/pool/IUniswapV3PoolImmutables.sol), [pool state](https://github.com/Uniswap/v3-core/blob/main/contracts/interfaces/pool/IUniswapV3PoolState.sol), and [factory](https://github.com/Uniswap/v3-core/blob/main/contracts/UniswapV3Factory.sol).

The agent's sandbox attempt returned `{"errorKind":"RPC_UNAVAILABLE","stage":"chain"}` because it cannot reach the owner's configured RPC from this environment; the owner's host run supplies the live evidence above. A real RPC failure reports only a bounded stage (`chain`, `block`, `factory`, `pool`, `tokens`, `confirmation`, or `validation`), never a provider error body or credential-bearing URL.

The next gate is unsigned LP action qualification. The [Uniswap LP guide](https://developers.uniswap.org/docs/liquidity/liquidity-provisioning-api/integration-guide) gives a v3 `/lp/create` request using `existingPool`, one token amount and a price or tick range; `/lp/check_approval` uses the wallet, token amounts and action. These two endpoints can be researched and probed without sending an on-chain transaction, provided the returned `TransactionRequest` is treated as untrusted data and never submitted. Increase and decrease require a real position NFT ID; fee claim also requires a position ID. Do not invent one or substitute another account's position to imply that the current wallet's flow works. For every response, independently check chain, wallet, position manager or approved spender, token order, calldata selector and decoded bounds, recipient, amounts, deadline and current state. A successful API response alone is not a broadcast approval. Define position discovery and fee freshness before display; do not infer USD TVL or APR from `poolLiquidity`.

`DEX_SMOKE_WALLET=0x... node scripts/smoke-lp-unsigned.mjs` is a narrow **unsigned API probe**. It requests a Polygon v3 position with 1 native USDC, full-range ticks and explicit 0.5% slippage, then asks for approval transactions using the returned token amounts. It never calls a wallet, signs, broadcasts, prints the key or prints returned calldata. A `shapeValid:true` result means only that the response has the expected outer fields; the separate `calldataReview` and approval policy fields report local semantic checks. The key and owner wallet are read from ignored environment configuration; an unfunded wallet may cause an upstream error, which is reported only by status/category.

The agent's network-restricted run returned `{ "stage": "create", "errorKind": "NETWORK" }`. The owner's host reached `/lp/create` with HTTP 200 and matching token amounts. The bounded diagnostic confirmed `chainId`, wallet, official v3 position-manager target and calldata shape; the only mismatch was `value`, which the next run classified as `zero-hex`. The probe accepts bounded decimal or hex zero while positive or malformed native values fail closed. The owner's latest run returned `shapeValid:true` for both create and approval, with `transactionCount:2`. This is the first live evidence of approval endpoint access; spender, allowance amount and create-call semantics were not in that output.

The calldata probe recognizes only a direct v3 `mint` call and checks token pair, fee 500, full-range ticks, desired amounts, positive minima within the requested 0.5% tolerance, recipient and a future deadline; unknown selectors or multicall remain unqualified. For each approval it decodes ERC20 `approve`, checks the token target and v3 position-manager spender, and reports `exact`, `unlimited` or another bounded amount kind. The owner's decoded live result was `callKind:"mint"`, with pair, fee, ticks, minima, recipient and deadline checks true, but `desiredAmountsMatch:false`. Both approvals target the manager and have `amountKind:"unlimited"`, so `approvalPolicyMatches:false`. The probe now reports only per-token direction and a bounded difference band (`one-unit`, `within-50-bps`, `over-50-bps`); the owner's host must rerun it to locate the mismatch. It continues to reject mismatched desired amounts and unlimited approvals.

The [v3 SDK mint builder](https://github.com/Uniswap/v3-sdk/blob/main/src/nonfungiblePositionManager.ts) derives desired amounts from `position.mintAmounts` and minima from `mintAmountsWithSlippage`; the [position manager](https://github.com/Uniswap/v3-periphery/blob/main/contracts/NonfungiblePositionManager.sol) supplies those desired values to `addLiquidity` and receives actual amounts back. Thus the decoded desired values are transaction input ceilings. We have **not** established whether the LP API's returned `token0.amount`/`token1.amount` denote rounded estimates or those ceilings. The independent 1-USDC user cap must be enforced against decoded `amount0Desired`; checking only the API response field is insufficient. Any later exact approval plan must be based on validated maximum input and pinned current allowance, with token-specific reset behavior; never sign the API's unlimited approvals. Current allowance, simulation, wallet execution and economic receipt still need separate checks. The ABI fields follow Uniswap's [position-manager interface](https://github.com/Uniswap/v3-periphery/blob/main/contracts/interfaces/INonfungiblePositionManager.sol) and [LP API guide](https://developers.uniswap.org/docs/liquidity/liquidity-provisioning-api/integration-guide).

The proposed read and write contracts, including a compact threat model and the launchpad UI reference for later work, are in the [Polygon v3 LP design](../specs/2026-09-30-polygon-v3-lp-design.md).
