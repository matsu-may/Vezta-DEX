# Polygon LP API feasibility — read-only gate

**Status:** The owner observed live HTTP 200 responses with one pool each. A bounded diagnostic showed all checked identity/state fields matched except token decimals, whose returned type was `string` while the probe required `number`. The probe now accepts only canonical `"6"`/`"18"` strings or the corresponding numbers in the correct token order; a fresh host run is needed to confirm the actual values and liquidity. No LP write code or wallet action is approved by this note.

The candidate is the native-USDC/WETH Uniswap v3 0.05% pool `0xA4D8c89f0c20efbe54cBa9e7e7a7E509056228D9`, identified in the earlier [pool research](2026-09-27-polygon-weth-usdc.md). Uniswap's [Polygon v3 deployment list](https://developers.uniswap.org/docs/protocols/v3/deployments/v3-polygon-deployments) identifies the `NonfungiblePositionManager` as `0xC36442b4a4522E871399CD717aBDD847Ab11FE88`. A swap route using this pool does not prove the LP API works for this pool.

The current [Uniswap LP integration guide](https://developers.uniswap.org/docs/liquidity/liquidity-provisioning-api/integration-guide) describes `/lp/check_approval`, `/lp/create`, `/lp/increase`, `/lp/decrease`, `/lp/claim_fees` and `/lp/pool_info`. It says approval and transaction validation remain the integrator's responsibility, with the user's wallet signing and broadcasting. Its v3 decrease flow may include fee collection; UI must avoid counting those fees twice. The [pool-info API](https://developers.uniswap.org/docs/api-reference/pool_info) accepts a v3 token pair, fee and chain ID and returns pool identity, tick and liquidity fields. The separate [v3 position-fetching guide](https://developers.uniswap.org/docs/sdks/v3/guides/managing-liquidity/position-fetching) documents owner NFT IDs and `positions(tokenId)` reads; it is not itself an indexed portfolio service.

`node scripts/smoke-lp-pool-info.mjs` makes exactly one authenticated, **read-only** request for Polygon 137, native USDC/WETH and fee 500. It validates the returned pool address, token addresses/decimals, protocol and live-state field shapes. It reads `UNISWAP_LP_API_KEY` if set, otherwise `UNISWAP_API_KEY`, from ignored `apps/api/.env`. The agent's restricted network returned `{"errorKind":"NETWORK"}`, but the owner's host returned `{"status":200,"poolCount":1,"poolMatches":false,"stateShapeValid":false,"activeLiquidityPositive":false}` twice. HTTP 200 establishes endpoint/key access for this read; the false flags **do not** establish which field differs or whether the candidate pool is wrong. The `stateShapeValid` and liquidity flags remain false whenever identity fails, so they are not separate evidence of empty liquidity.

The bounded `poolChecks` output identified: Polygon chain, v3 protocol, expected pool address, native-USDC/WETH pair, fee and state field shapes matched; `tokenDecimalsMatch` was false with `tokenDecimalsTypes:["string","string"]`. The probe now checks exact expected decimal values as numbers or canonical strings, preserving rejection of wrong values, reversed token-decimal mappings and noncanonical strings such as `"06"`. It prints `poolChecks` **only on mismatch** and never prints the API key, wallet, request ID, arbitrary upstream strings, raw response or transaction data. Run it once more; do not approve the pool until it passes and a pinned Polygon read independently confirms identity. Uniswap's [pool-info API reference](https://developers.uniswap.org/docs/api-reference/pool_info) documents the requested token pair, fee, chain and response fields used by this probe.

Even a matching `/lp/pool_info` result is only the first LP gate. Before enabling a position UI or wallet controls, verify access and exact unsigned response shapes for approval, create, increase, decrease and claim on Polygon; validate the manager/spender/calldata/recipient/amount bounds independently; define position discovery and fee freshness; then test on a wallet/fork. Do not infer USD TVL or APR from the returned `poolLiquidity` field.

The proposed read and write contracts, including a compact threat model and the launchpad UI reference for later work, are in the [Polygon v3 LP design](../specs/2026-09-30-polygon-v3-lp-design.md).
